# 0. Agent Action Plan

## 0.1 Intent Clarification


### 0.1.1 Core Feature Objective

Based on the prompt, the Blitzy platform understands that the new feature requirement is to integrate the Express.js web framework into an existing bare-bones Node.js tutorial server and extend its HTTP API surface with an additional greeting endpoint. Specifically:

- **Integrate Express.js framework**: The existing project is described by the user as a Node.js server that hosts a single endpoint returning `"Hello world"`. The platform interprets this as a requirement to adopt Express.js as the HTTP framework, replacing or wrapping any native `http.createServer()` usage with the Express application factory pattern (`express()`) and Express Router (`express.Router()`).
- **Add a new `GET /evening` endpoint**: A second HTTP GET endpoint must be created that responds with the exact string `"Good evening"` when accessed. This endpoint must coexist with the original root endpoint without altering its existing behavior.
- **Preserve existing behavior**: The original `GET /` endpoint must continue to return its `"Hello, World!\n"` response with byte-level fidelity, including the trailing newline character. The integration of Express.js and the addition of the new endpoint must not break backward compatibility.
- **Implicit requirement — Modular architecture**: Adopting Express.js implies transitioning from a monolithic single-file server to a modular architecture that separates concerns: application configuration, server binding, routing, and environment configuration.
- **Implicit requirement — Testability**: The Express.js factory pattern enables unit testing the application without starting an HTTP server, which is an inherent benefit of the migration.

### 0.1.2 Special Instructions and Constraints

- **No explicit architectural directives provided**: The user did not specify a particular design pattern. The platform follows established Express.js conventions: factory pattern for the app, barrel pattern for route aggregation, and Twelve-Factor App methodology for configuration.
- **No backward compatibility constraints stated**: However, the platform infers that the original `GET /` response (`"Hello, World!\n"`) must remain unchanged since the user only requested an *addition*.
- **Module system**: The existing project uses CommonJS (`require`/`module.exports`). All new and modified files must maintain CommonJS compatibility.
- **User Example — Original endpoint**: `GET /` → `"Hello, World!\n"` (with trailing newline, 14 bytes)
- **User Example — New endpoint**: `GET /evening` → `"Good evening"` (no trailing newline, 12 bytes)

### 0.1.3 Technical Interpretation

These feature requirements translate to the following technical implementation strategy:

- To **integrate Express.js**, we will add `express@^5.1.0` as a runtime dependency in `package.json`, create an application factory module (`src/app.js`) that constructs and exports a configured Express application, and refactor `server.js` to import and bind this application instead of using native `http.createServer()`.
- To **add the `/evening` endpoint**, we will create a dedicated route handler module (`src/routes/main.routes.js`) using `express.Router()` that registers both `GET /` and `GET /evening` handlers, and aggregate route exports through a barrel module (`src/routes/index.js`).
- To **externalize configuration**, we will create a configuration module (`src/config/index.js`) that reads `HOST`, `PORT`, and `NODE_ENV` from environment variables with sensible defaults (`127.0.0.1`, `3000`, `development`), following Twelve-Factor App principles.
- To **maintain the project structure**, we will organize source code under a `src/` directory with clear separation: `src/app.js` (Express factory), `src/config/` (configuration), and `src/routes/` (routing surface).

### 0.5.2 Implementation Approach per File

**Step 1 — Establish route handlers (`src/routes/main.routes.js`):**

Create the Express Router with both endpoint handlers. This is the core of the new feature:

```javascript
const router = require('express').Router();
router.get('/', (req, res) => res.send('Hello, World!\n'));
router.get('/evening', (req, res) => res.send('Good evening'));
```

**Step 2 — Create route barrel (`src/routes/index.js`):**

Aggregate route exports for clean import by the application factory:

```javascript
const mainRoutes = require('./main.routes');
module.exports = { mainRoutes };
```

**Step 3 — Create application factory (`src/app.js`):**

Instantiate Express and mount routes. The factory pattern keeps `listen()` out of this module for testability:

```javascript
const app = require('express')();
app.use('/', require('./routes').mainRoutes);
```

**Step 4 — Create configuration module (`src/config/index.js`):**

Externalize host, port, and environment to follow Twelve-Factor methodology:

```javascript
module.exports = {
  host: process.env.HOST || '127.0.0.1',
  port: parseInt(process.env.PORT, 10) || 3000
};
```

**Step 5 — Refactor server entry point (`server.js`):**

Replace native `http` usage with Express app import and config-driven binding:

```javascript
const app = require('./src/app');
const config = require('./src/config');
app.listen(config.port, config.host, () => { /* log */ });
```

**Step 6 — Update `package.json`:**

Add Express.js as the sole runtime dependency with semver range `^5.1.0`.

**Step 7 — Update `README.md`:**

Expand documentation to cover the Express.js architecture, both endpoints, environment variables, project structure diagram, and troubleshooting guidance.

## 0.7 Rules for Feature Addition


### 0.7.1 Feature-Specific Rules and Requirements

The user did not specify explicit rules or constraints beyond the feature request itself. The following rules are derived from the project's established conventions and the implicit requirements of the Express.js integration:

**Behavioral Parity Rules:**

- The `GET /` endpoint MUST return the exact string `Hello, World!\n` (14 bytes, including the trailing newline character). Any deviation breaks the original contract.
- The `GET /evening` endpoint MUST return the exact string `Good evening` (12 bytes, no trailing newline). This matches the user's explicit request.
- Both endpoints MUST respond with HTTP status `200 OK` and Express.js default `Content-Type: text/html; charset=utf-8`.

**Architectural Convention Rules:**

- All source files MUST use CommonJS module syntax (`require()` / `module.exports`). No ESM (`import`/`export`) syntax is permitted.
- The application factory (`src/app.js`) MUST NOT call `app.listen()`. Server binding is the sole responsibility of `server.js`.
- The route aggregator (`src/routes/index.js`) MUST export routes using named properties (e.g., `{ mainRoutes }`) to support destructured imports.
- The configuration module (`src/config/index.js`) MUST be synchronous with no async initialization, I/O, or side effects beyond reading `process.env`.

**Dependency Rules:**

- Express.js MUST be pinned to semver range `^5.1.0` (allowing patch and minor updates within the 5.x line).
- No additional npm packages beyond `express` may be added as direct dependencies.
- The `package-lock.json` MUST be committed to ensure deterministic installs via `npm ci`.

**Runtime Compatibility Rules:**

- The project MUST run on Node.js ≥18.x, with Node.js 20.19.x LTS as the recommended version.
- Default server binding MUST be `127.0.0.1:3000` when no environment variables are set.
- Environment variable overrides (`HOST`, `PORT`, `NODE_ENV`) MUST be supported without code changes.
